## 补记 3：Release/AOT 构建受阻（上游 bug，待办）

**现象**：Release 构建在 javac 阶段失败：`需要包含 WallpaperService.Engine 的封闭实体 / super(p0)`。

**根因**（已完全定位）：`WallpaperService.Engine` 是 **Java 内部类**（构造无参、隐式捕获外部实例）。dotnet/android 的 Release ACW 生成器（`GenerateJavaStubs`）把 C# 绑定构造 `Engine(WallpaperService __self)` 直译为顶层桥接类的 `super(p0)`——Java 语法禁止顶层类继承内部类，javac 必然失败。**Debug 不受影响**：FastDev 模式只生成 manifest 引用类型（Service）的最小 ACW，Engine 子类走运行时注册。

**已尝试无效的方案**：补 `(IntPtr, JniHandleOwnership)` 构造、`[Register("...$VideoEngine")]` 内部类路径注册、`UseInterpreter`（不阻止 ACW 生成）。

**候选解决路径**（待办，按成本递增）：
1. 跟踪 dotnet/android 上游 issue / 升级 workload 版本重试；
2. 手写双 Java 桥（`DoNotGenerateAcw` + `AndroidJavaSource` 手写 Service/Engine 内部类声明，照生成器模板修正 super() 语义）——注意 Engine 封闭实例语义风险；
3. 上游无人修复时的终极方案：Java 层手写壁纸服务 + C# 通过绑定库调用。

**内存基线（Debug 版，进程 PSS）**：`dumpsys meminfo` → **TOTAL PSS 159 MB**（含 Mono 解释器 + JIT 开销）。AOT 后预期 60~90MB（.NET Android AOT 常态），**正式验收数字等 Release 通路修复后复测**。

## 补记 5：Release/AOT 通路攻克 ✅ + 内存验收达标 ✅（2026-10-25 深夜续）

**最终方案：构建后处理改写 ACW（`fix-acw.ps1` + `FixEngineAcw` MSBuild target）**，绕过上游生成器 bug：

1. `AfterTargets="_GenerateJavaStubs"` 钩子改写生成产物：
   - 把非法的顶层 `VideoWallpaperService_VideoEngine.java` 改写后**注入** `VideoWallpaperService.java` 内部（内部类声明——Java 语法要求内部类子类必须在外围类内）；
   - **Java 8 兼容化**：删除 static 字段与 static 初始化块（Java 16 前内部类禁止 static 成员），`Runtime.register` 移入构造器、`__md_methods` 字符串内联（字符串内分号需引号状态机提取，防截断）；
   - **构造形态对齐 Debug 运行时**（实机日志取证：`Java 层类名 = ...$VideoWallpaperService_VideoEngine`）：无参构造 + `TypeManager.Activate(..., VideoWallpaperService.this)`（外围实例传给 C# 绑定构造）——错误的 `(WallpaperService p0)` 参数形态会导致 JNI `NoSuchMethodError`（内部类构造签名含隐式外围参数）；
   - C# 侧 `[Register("com.wallpaperengine.app.VideoWallpaperService$VideoWallpaperService_VideoEngine")]` 固定运行时类名；幂等保护防增量重复注入。

2. **踩坑记录**：`AndroidLinkTool=None`（测试链接器假说时的残留）会破坏 dex 组装（`MonoRuntimeProvider` 缺失），已删除；增量构建会跨轮次污染产物，**Release 构建异常时先删 obj/bin 全新构建**。

**真机验证（Reno6 Pro，Release/AOT 版）**：
- 引擎全链路正常（OnCreateEngine → 配置热重载 → 装载 → Prepared；用户连换两个视频均即时切换）；
- APK 含 39 个 AOT 原生库（libaot-*.so，AOT 编译确认生效）。

## 补记 8：Android 16 强制 edge-to-edge 适配修复（2026-10-25，用户在 Neo 9 上发现）

**现象**：Neo 9（Android 16）上左上角标题/副标题与右上角 ☰ 按钮不可见。UI dump 证实元素层级与坐标正常（标题 y=60 起）——**被系统状态栏覆盖**。

**根因**：Android 15+ 强制 edge-to-edge（内容默认绘制到状态栏/导航栏底下），未处理 insets 的界面顶部被系统栏遮挡。Android 13（Reno6 Pro）无此强制行为，故从未暴露。

**修复**：`SystemBarsInsetListener`（`View.IOnApplyWindowInsetsListener`）把系统栏高度转为根容器 padding，新旧系统行为统一。验证：标题 y 60→348（让出 288px 状态栏），全部元素可见，用户确认。
（绑定 API 注意：`WindowInsets` 的 insets 取值是**属性形式** `SystemWindowInsets`/`SystemWindowInsetTop`，非 Get 方法。）

## 补记 10：双槽壁纸功能尝试与回退（2026-10-25 深夜）

**功能**：桌面/锁屏分别设置不同视频（配置双槽 + 选壁纸时范围三选 + 引擎可见性时序自识别身份）。

**实现路径**：`LockVideoPath` 锁屏槽（空=跟随桌面）；引擎经场景广播（SCREEN_ON/USER_PRESENT）+ 可见性时序识别自身是桌面端还是锁屏端，各读各槽。先后修复：槽快照语义（单独设置一端时另一端固化）、识别竞速（延迟 500ms 判定）。

**结果：真机实测仍不生效（锁屏槽读了旧值/不切换），用户决策回退。** 回退后恢复单一壁纸模式，保留：自定义默认壁纸、历史删除、深色菜单、按钮改名。

**经验沉淀**：
1. 基于系统行为逆向推断（引擎身份启发式）的方案脆弱性高：ColorOS 的锁屏引擎可见性时序不受契约保障，竞速修补无法穷尽；
2. 此功能的正确打开方式需要系统级支持（如 ROM 开放锁屏 live wallpaper 的区分 API），社区暂无成功先例可抄；
3. 工程决策：实测两轮不过即回退，保留可用的单一模式——避免在启发式泥潭里持续投入（用户拍板，正确）。

### 下午：历史管理增强（用户驱动）
5. **历史删除**：长按 → 确认 → 删除条目并清理视频/缩略图；正在使用与默认壁纸保护；
