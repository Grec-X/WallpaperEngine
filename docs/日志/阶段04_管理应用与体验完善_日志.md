## 补记 3：Release/AOT 构建受阻（上游 bug，待办）

**现象**：Release 构建在 javac 阶段失败：`需要包含 WallpaperService.Engine 的封闭实体 / super(p0)`。

**根因**（已完全定位）：`WallpaperService.Engine` 是 **Java 内部类**（构造无参、隐式捕获外部实例）。dotnet/android 的 Release ACW 生成器（`GenerateJavaStubs`）把 C# 绑定构造 `Engine(WallpaperService __self)` 直译为顶层桥接类的 `super(p0)`——Java 语法禁止顶层类继承内部类，javac 必然失败。**Debug 不受影响**：FastDev 模式只生成 manifest 引用类型（Service）的最小 ACW，Engine 子类走运行时注册。

**已尝试无效的方案**：补 `(IntPtr, JniHandleOwnership)` 构造、`[Register("...$VideoEngine")]` 内部类路径注册、`UseInterpreter`（不阻止 ACW 生成）。

**候选解决路径**（待办，按成本递增）：
1. 跟踪 dotnet/android 上游 issue / 升级 workload 版本重试；
2. 手写双 Java 桥（`DoNotGenerateAcw` + `AndroidJavaSource` 手写 Service/Engine 内部类声明，照生成器模板修正 super() 语义）——注意 Engine 封闭实例语义风险；
3. 上游无人修复时的终极方案：Java 层手写壁纸服务 + C# 通过绑定库调用。

**内存基线（Debug 版，进程 PSS）**：`dumpsys meminfo` → **TOTAL PSS 159 MB**（含 Mono 解释器 + JIT 开销）。AOT 后预期 60~90MB（.NET Android AOT 常态），**正式验收数字等 Release 通路修复后复测**。

## 补记 5：Release/AOT 通路攻克 ✅ + 内存验收达标 ✅（2026-10-25 深夜续）

**最终方案：构建后处理改写 ACW（`fix-acw.ps1` + `FixEngineAcw` MSBuild target）**，绕过上游生成器 bug：

1. `AfterTargets="_GenerateJavaStubs"` 钩子改写生成产物：
   - 把非法的顶层 `VideoWallpaperService_VideoEngine.java` 改写后**注入** `VideoWallpaperService.java` 内部（内部类声明——Java 语法要求内部类子类必须在外围类内）；
   - **Java 8 兼容化**：删除 static 字段与 static 初始化块（Java 16 前内部类禁止 static 成员），`Runtime.register` 移入构造器、`__md_methods` 字符串内联（字符串内分号需引号状态机提取，防截断）；
   - **构造形态对齐 Debug 运行时**（实机日志取证：`Java 层类名 = ...$VideoWallpaperService_VideoEngine`）：无参构造 + `TypeManager.Activate(..., VideoWallpaperService.this)`（外围实例传给 C# 绑定构造）——错误的 `(WallpaperService p0)` 参数形态会导致 JNI `NoSuchMethodError`（内部类构造签名含隐式外围参数）；
   - C# 侧 `[Register("com.wallpaperengine.app.VideoWallpaperService$VideoWallpaperService_VideoEngine")]` 固定运行时类名；幂等保护防增量重复注入。

2. **踩坑记录**：`AndroidLinkTool=None`（测试链接器假说时的残留）会破坏 dex 组装（`MonoRuntimeProvider` 缺失），已删除；增量构建会跨轮次污染产物，**Release 构建异常时先删 obj/bin 全新构建**。

**真机验证（Reno6 Pro，Release/AOT 版）**：
- 引擎全链路正常（OnCreateEngine → 配置热重载 → 装载 → Prepared；用户连换两个视频均即时切换）；
- APK 含 39 个 AOT 原生库（libaot-*.so，AOT 编译确认生效）。

## 补记 8：Android 16 强制 edge-to-edge 适配修复（2026-10-25，用户在 Neo 9 上发现）

**现象**：Neo 9（Android 16）上左上角标题/副标题与右上角 ☰ 按钮不可见。UI dump 证实元素层级与坐标正常（标题 y=60 起）——**被系统状态栏覆盖**。

**根因**：Android 15+ 强制 edge-to-edge（内容默认绘制到状态栏/导航栏底下），未处理 insets 的界面顶部被系统栏遮挡。Android 13（Reno6 Pro）无此强制行为，故从未暴露。

**修复**：`SystemBarsInsetListener`（`View.IOnApplyWindowInsetsListener`）把系统栏高度转为根容器 padding，新旧系统行为统一。验证：标题 y 60→348（让出 288px 状态栏），全部元素可见，用户确认。
（绑定 API 注意：`WindowInsets` 的 insets 取值是**属性形式** `SystemWindowInsets`/`SystemWindowInsetTop`，非 Get 方法。）

## 补记 10：双槽壁纸功能尝试与回退（2026-10-25 深夜）

**功能**：桌面/锁屏分别设置不同视频（配置双槽 + 选壁纸时范围三选 + 引擎可见性时序自识别身份）。

**实现路径**：`LockVideoPath` 锁屏槽（空=跟随桌面）；引擎经场景广播（SCREEN_ON/USER_PRESENT）+ 可见性时序识别自身是桌面端还是锁屏端，各读各槽。先后修复：槽快照语义（单独设置一端时另一端固化）、识别竞速（延迟 500ms 判定）。

**结果：真机实测仍不生效（锁屏槽读了旧值/不切换），用户决策回退。** 回退后恢复单一壁纸模式，保留：自定义默认壁纸、历史删除、深色菜单、按钮改名。

**经验沉淀**：
1. 基于系统行为逆向推断（引擎身份启发式）的方案脆弱性高：ColorOS 的锁屏引擎可见性时序不受契约保障，竞速修补无法穷尽；
2. 此功能的正确打开方式需要系统级支持（如 ROM 开放锁屏 live wallpaper 的区分 API），社区暂无成功先例可抄；
3. 工程决策：实测两轮不过即回退，保留可用的单一模式——避免在启发式泥潭里持续投入（用户拍板，正确）。

## 补记 16：双状态卡"直读系统真实壁纸"（2026-10-25 深夜，用户反馈驱动）

**问题**：双状态卡基于本地跟踪推断，与系统实际状态脱节（Neo 9 上锁屏引擎存活 + 桌面静态的场景，桌面卡误显示视频；跟踪字段对系统页/旧版本操作不感知）。

**修复**：`TryGetActualWallpaperBitmap(FLAG)` —— `WallpaperManager.GetWallpaperFile(which)` **直读系统各槽当前静态壁纸**，卡片缩略图直接渲染系统真实画面；名称用本地跟踪、画面以系统为准。

**权限坑（两层）**：
1. Android 13+ 将 `GetWallpaperFile` 划入 **READ_MEDIA_IMAGES** 媒体权限组——未授权抛 SecurityException，双卡回落视频分支（用户报告的"永远显示视频"即此）；manifest 补声明 + 运行时请求（旧版本 READ_EXTERNAL_STORAGE maxSdkVersion=32）；
2. 修复期间权限代码缺 `Android.Content.PM` using 导致构建失败、APK 未更新，误装旧包——**教训：构建验证必须看真实错误行 + APK 时间戳，不能只看"0 个错误"字样（失败构建的汇总行也可能显示旧缓存内容）**；`BitmapFactory.DecodeFileDescriptor(pfd.FileDescriptor)` 直解（绑定流类型不走 System.IO.Stream）。

**验证**：Neo 9 上桌面卡=静态图片（系统当前，真实画面）、锁屏卡=跟随桌面（动态），两卡内容不同且与实际一致；`pm grant` 预授权后无任何 GetWallpaperFile 异常。Reno6 Pro（ColorOS 13.1）对此 API 的行为待连机验证（try/catch + 回退已兜底）。

## 补记 17：视频目标应用"去定格化"（2026-10-25 深夜，用户产品决策）

**用户决策**："视频壁纸应该是视频的"——应用流程的终点永远是视频在动态播放，定格帧不是合法的落地形态，移除。

**语义变化**：以 Neo 9（桌面静态+锁屏动态状态）为例——"设置为桌面壁纸"现在会拉起确认页，确认后桌面**动态**播放该视频（旧逻辑是静态帧+引导提示，已废除）。

## 补记 18：待应用路由架构（2026-10-25 深夜，用户方案定稿并实施）

**用户方案**：点击视频 → 直达系统确认页（范围在系统页选择）→ 软件**反向读取系统实际绑定**，把视频路由到对应槽——省去软件自身的选择菜单。

**实现**：
1. 配置新增 Pending 组字段（PendingVideoPath/Name/DurationMs/At，15 分钟过期）；
2. 点击视频（收藏/历史/选择壁纸统一）→ 暂存 pending → `RequestSetWallpaper()` 直达确认页；
3. **主路径**：返回 App（OnResume）→ `getWallpaperInfo(FLAG_SYSTEM/FLAG_LOCK)` 读系统已记录的绑定范围（确认即写数据，无需引擎已绑定）→ 按范围把 pending 写入对应槽 → NotifyConfigChanged → 引擎各播各槽；
4. **兜底**：getWallpaperInfo 不可用的 ROM → 引擎注册事件（含延迟绑定的锁屏引擎）触发 `GetActiveEngineFlags()` 身份路由；
5. 三选菜单/VideoTarget/ApplyVideoToTarget 整体移除；图片静态菜单保留（图片无法走动态确认页）。

**时序说明**（对用户疑问的回应）：锁屏引擎绑定（真正开始渲染）在下次锁屏亮起——物理时机不可改；但范围数据在确认瞬间已写入系统（dumpsys 实证），卡片经 getWallpaperInfo 主路径**返回即更新**；仅当 ROM 破坏该 API 时卡片延迟到引擎注册时更新（感知无损）。

## 补记 19：待应用路由方案实测失败与回退（2026-10-25 深夜，用户实测）

**实测结果**（用户报告，双 bug）：
1. 确认页预览总是显示旧/默认视频——pending 设计下点击的视频未写入任何槽，预览引擎装载的是槽内旧配置；
2. **未点系统页"应用"，锁屏已变为所点视频**——`getWallpaperInfo(which)` 返回的是**已存在的绑定**（锁屏此前就有我们的动态绑定），返回 App 时的消费逻辑无法区分"本次新选择"与"既有状态"，也无法区分"确认"与"取消"。

**结论：读系统回显路线在框架层面不可行**——系统页的范围选择指挥的是绑定，而绑定状态无法与历史状态区分；且确认页无结果返回（无法判定确认/取消）。用户"读系统设置来调整卡片"的设想经实测证伪，归档。

**回退落地**：恢复三选目标菜单（桌面壁纸/锁屏壁纸/桌面和锁屏壁纸）+ 双槽写入（补记 15 架构，Neo 9 实测可用）。修复确认页预览问题：绑定缺失时**先预写槽配置再拉起确认页**（预览引擎装载即所点视频）。`ConsumePendingApply`/pending 消费逻辑整体移除（Core 的 Pending 字段保留不用，作方案档案）。

**经验**：系统确认页是 fire-and-forget——无结果返回、无范围查询 API；任何"确认后再读回"的设计都会撞上"既有状态污染"。ROM 对动态壁纸的分端控制是写路径特权（系统页内部），读路径不开放。软件内三选菜单（按槽写配置）是当前架构下唯一可靠的分端方式。

## 补记 21：静态图片设为桌面默认后"恢复桌面默认"冻结 bug——原因报告（2026-10-26，未动代码）

**复现路径**：桌面为静态壁纸 → 历史中选视频 A 设为桌面默认 → 恢复桌面默认（确认页选桌面）→ 桌面动态播 A ✓ → 历史中选静态图片 B 设为桌面默认 → 恢复桌面默认 → **bug**：桌面未变成图片 B，而是停留在视频 A 的某一帧（形似"视频暂停"）；芯片显示"桌面 · 动态运行中"；卡片缩略图是 B 但状态文字是"动态视频"。点 B → 设为桌面壁纸（静态提交）后恢复。

**原因链条**（已定位，未动代码）：
1. `SetAsDefault` 只存路径，不区分媒体类型——`DefaultVideoPath = 图片B 路径`；
2. `ResetSlotDefault(Desktop)` 复用 `ApplyVideoToTarget`，该函数假定所有默认条目都是**可播放视频**，把图片 B 的路径写进了 `VideoPath`（视频槽配置）并 NotifyConfigChanged；
3. 桌面引擎重装载 → ExoPlayer 尝试把**图片文件当视频解码** → Source error → 错误处理重试一次后放弃 → Surface 停留在**上一视频的最后一帧**——即用户看到的"动态壁纸暂停"假象；
4. 引擎实例本身存活（绑定、生命周期正常）→ 芯片如实显示"动态运行中"（引擎确实在，只是源错误）；
5. 卡片缩略图走 `SetCardThumb(VideoPath=图片B)` → 图片解码分支正常出图 → 卡片显示 B 的缩略图，但状态文字按配置槽类型写作"动态视频"——图文错位。

**根本原因（设计缺口）**：默认壁纸不区分**媒体类型与渲染形态**。桌面槽存在两种合法形态（动态=引擎播视频 / 静态=SetBitmap 提交图片），"桌面默认"也应有两类：默认视频（恢复→引擎播放）与默认图片（恢复→静态提交）。当前单一 `DefaultVideoPath` 把图片当视频喂给引擎是错误源头。

**附带发现**：`ResolveVideoPath` 对槽内非视频文件（图片）无防御——任何路径把图片写进 VideoPath 都会造成"冻结帧"状态，且该状态跨引擎重启持续（每次装载都失败）。

**修复方向（待确认后实施）**：
1. `SetAsDefault` 记录条目 MediaType（`DefaultMediaType` 字段）；
2. `ResetSlotDefault` 按 MediaType 路由：Image → `ApplyImageAsStatic(FLAG_SYSTEM)`；Video → `ApplyVideoToTarget`；
3. 防御：`ResolveVideoPath` 校验槽内文件扩展名，非视频回退默认素材；
4. 体验增强（可选）：ErrorOccurred 后芯片显示"桌面 · 播放异常"；
5. 恢复用户设备现状：需重新应用任一视频为桌面壁纸（或重装清数据）。

## 补记 22：补记 21 冻结 bug 修复落地（2026-10-26）

按原因报告的四项方向实施：

1. **媒体类型记录**：`WallpaperConfig.DefaultMediaType`（Video/Image）；`SetAsDefault` 写入 `entry.MediaType`；
2. **恢复按类型路由**：`ResetSlotDefault` 判定 `DefaultMediaType == "Image"` → `ApplyImageAsStatic(FLAG_SYSTEM/FLAG_LOCK)`（静态提交）；否则走 `ApplyVideoToTarget`（引擎播放）——图片不再被喂给 ExoPlayer；

## 补记 23：恢复默认误判"已是默认"（2026-10-26，用户实测）

**复现**：桌面为静态图 + 桌面默认为视频 → 点「恢复桌面默认」→ 提示"桌面已是默认壁纸"、桌面不变。

**规律沉淀**：本项目 3 个同源 bug（补记 20 角标、21 媒体类型、23 恢复误判）都源于"配置记录 ≠ 实际渲染状态"。**判定 UI 与操作前置条件时，必须读系统实际状态（GetWallpaperFile / GetActiveEngineStatus），配置只作名称与意图参考。**

## 补记 25：重启后锁屏状态与亮屏黑屏（2026-10-26，用户反馈 + 实测定位）

**现象一：重启手机后锁屏动态壁纸变成静态**

实测 `dumpsys wallpaper`（重启后 1 分钟）：
```
System: mWhich=1, mBindSource=SET_STATIC      → ImageWallpaper
Lock:   mWhich=2, mBindSource=SWITCH_WALLPAPER_UNLOCK_USER → 我们的引擎
```
锁屏动态绑定**没有丢失**，但恢复时机是 `SWITCH_WALLPAPER_UNLOCK_USER`——系统在**用户首次解锁后**才切换锁屏壁纸。重启后到首次解锁之间，锁屏显示的是系统回退壁纸（静态）。这是 OriginOS 的重启恢复策略：先保证锁屏界面可用，解锁后再应用动态壁纸。**应用层无法改变**。

**现象二：亮屏时黑屏约 2 秒后才出现动态壁纸**

logcat 冷启动时间线（一次亮屏）：
```
13:38:34.249 OnCreate（引擎创建，读配置）
13:38:34.479 OnSurfaceCreated（Surface 就绪）
13:38:34.552 已装载视频（SetDataSource）
13:38:36.639 [ExoPlayer] Prepared（首次解码就绪）  ← 距 Surface 就绪 2.16 秒
```
这 2.16 秒内 Surface 没有任何内容，所以是黑的。耗时来自：ExoPlayer 实例化 → MediaCodec 硬件解码器初始化 → 打开文件读取元数据 → 解码首帧。

**修复：占位帧**

`OnSurfaceCreated` 里在 `SetSurface`/`Prepare` **之前**，用 `Surface.LockCanvas` 把该槽缩略图按 Cover 比例画上去，视频首帧上屏后自然覆盖。暖启动（Surface 重建）时也能立刻出画。

配套：`WallpaperConfig` 增加 `ThumbPath` / `LockThumbPath`，应用壁纸时写入（`EnsureThumbPathFor`）。老配置没有这两个字段，引擎按视频内容 MD5 推导缩略图路径并缓存（与 App 侧命名一致）。

**新踩的坑：`am force-stop` 会丢弃锁屏动态绑定**

测试时用 `am force-stop` 重启壁纸服务，结果锁屏槽的动态绑定直接消失（`Lock` 段消失，锁屏变「未设置」）。ColorOS/OriginOS 对被强杀的壁纸服务不做重绑。因此**验证壁纸冷启动必须用重启手机，不能用 force-stop**。本次测试中用户锁屏壁纸因此丢失，需重新设置一次。

## 补记 26：占位帧方案失败与回退（2026-10-26，用户实测反馈）

**方案**：在 `OnSurfaceCreated` 里用 `Surface.LockCanvas` 把缩略图按 Cover 画到壁纸 Surface 上，视频首帧出来自然覆盖，以消除约 2 秒黑屏。

**实测结果**：选择动态壁纸后提示「锁屏播放异常」，画面停在缩略图不动——**视频根本没播起来**。

**原因**：Surface 只有一个生产者端。Canvas（`lockCanvas/UnlockCanvasAndPost`）和 MediaCodec 都要当生产者，Canvas 先占用后 MediaCodec 无法申请缓冲区，解码输出失败，Surface 上残留的就是那张缩略图。`SetSurface` 在 Canvas 之后调用，两者冲突无解。

**回退**：删除 `DrawPlaceholder` 与 `ResolvePlaceholderPath`，`OnSurfaceCreated` 恢复原流程，并在代码处留注释说明"不可对 Surface 用 LockCanvas"。

**结论**：壁纸 Surface 只能由单一生产者（MediaCodec 或 GL）渲染。要画占位帧必须自己搭 GL 渲染管线（OpenGL 纹理先画缩略图再接受解码输出），成本高、收益只有 2 秒观感改善，暂不做。**约 2 秒黑屏是框架层冷启动固有行为，接受**。

**保留**：`WallpaperConfig.ThumbPath / LockThumbPath` 字段（无害，将来若引入 GL 渲染可直接复用）。

**教训**：MediaCodec 与 Canvas 不可共用同一 Surface；Android 官方文档对此有说明（`lockCanvas` 会干扰 Surface 的 buffer 生产）。改动图形管线前应先查框架约束，而不是先试。

## 补记 27：开机首次 Prepare 卡死 + 看门狗重试 + 「加载中」状态（2026-10-26）

**现象**：换 720p 视频后重启手机，锁屏壁纸一直是空白/静态，App 芯片却显示「动态运行中」。

**实测数据**：
```
13:56:07.773 OnCreate（开机后系统绑定引擎）
13:56:08.548 OnSurfaceCreated
13:56:08.871 已装载视频[Lock]: wallpaper_20261026_135445.mp4
13:56:09.219 visible=True → 09.239 visible=False（20ms 内反复）
13:56:09.891 MediaCodec [c2.qti.avc.decoder] configure
13:56:09.924 MediaCodec start
（之后 10+ 秒无 Prepared，视频从未出帧）
```
同期系统 load average = 56（开机高峰）。可见性在 20ms 内 True→False 反复切换。

**结论**：解码器已启动但 ExoPlayer 未进入 READY——开机高峰 CPU 争抢 + 锁屏可见性抖动导致首帧渲染拿不到资源。重新应用同一视频时 Prepared 仅用 296ms，证明文件与管线均正常，属**启动时机问题**。

**芯片误导**：芯片只判断引擎实例存在即显示「动态运行中」，不判断是否真正出帧。

**两项修复**：
1. **Prepare 看门狗**：`Prepare()` 后 6 秒若 `DurationMs == 0`（未就绪），重新装载重试，最多 2 次（`_prepareRetries`），Prepared 成功即清零。防死循环、防无限重试。
2. **芯片三态**：`EngineStatus` 增加 `Ready`（`DurationMs > 0`）；芯片显示「播放异常」（有 Error）> 「加载中」（引擎在但未就绪）> 「动态运行中」（已就绪）> 静态/未设置。

**验证**：新 APK 安装后引擎重启，芯片先显示「锁屏 · 加载中」，约 2 秒 `Prepared` 成功后自动转「锁屏 · 动态运行中」。

**未测完**：720p 视频的首帧耗时对比（本次因 Prepare 卡死未拿到数据）。需再重启一次手机，在开机高峰过去后测量；若看门狗生效，最多多等 6 秒即自动恢复。
